Deja · agent context layer · built on HydraDB

Your agent has 2,000 tools.
Load the ones it will actually call.

Deja remembers, in a HydraDB graph, which tools past tasks actually needed: each task and the tools it used, which words led to which tools, and which tools get used together. A new task pulls the tools its most similar past tasks used. Every task it serves makes the next loadout sharper.

Gets sharper the more it is used

Share of tasks where every tool the agent ended up calling was already in its first loadout (2,000-token budget). Prequential: each task is scored before Deja learns from it. Buckets are log-spaced so the cold start is visible; band = 3 shuffles of the stream.

What does the work

Memory of past tasks does most of the lifting. A plain vector store of past tasks (no graph: the 20 nearest past tasks vote for the tools they used) already beats tool search by a wide margin. Deja keeps that memory in the graph and adds two hops on top: about 2.5 points overall and 3 on tasks that span two servers, mostly from the word hop.

How it works

(:Task) -[:USED]-> (:Tool)                                    every past task and the tools it called
(:Term {df}) -[:LED]-> (:Link {n}) -[:TO]-> (:Tool {uses})    a word in past tasks → the tool that solved them
(:Tool) -[:CO]-> (:CoLink {n}) -[:TO]-> (:Tool)               tools used together in one task
  • Query: embed the task. (1) Find the 20 most similar past tasks by embedding, then read their USED edges from HydraDB: they vote for tools. (2) Take the top 5 of that fused ranking and walk CO edges to the tools they're usually used with (about +1 point). (3) Walk LED edges from the task's 8 rarest words (about +3 points on multi-server tasks). Rank, pack to the token budget.
  • Learning: after each task, a Task node and its USED edges are added, and the word and co-use counts update.
  • Store: counts live on reified Link nodes because HydraDB batch writes set node properties but not edge properties. The vote hop is an id-only batched read. Every loadout served here is checked identical to an in-memory twin on the 200 held-out tasks; the 8,612-task curves use that twin.
  • Weights (not tuned per ordering): vote weight 1.0 and K=20 come from one check on shuffle 1; term weight 0.5 and co-use weight 0.2 are unchanged from v1.
  • Data: Toucan-1.5M: real MCP servers, real executed tool calls. 8,612 unique prompts (one per prompt_id; only 36 duplicate question texts, 1.8% have an earlier task at cosine ≥ 0.95), 2,236 tools across 367 servers, pooled into one catalog.

Under load

What we measured and threw away

  • Shared entity memory ("reuse IDs other agents resolved") was our first headline. It failed its own kill test: binding precision 21%, and even a perfect binder saves only 6.3% of lookups beyond a plain (tool, args) cache.
  • Data-flow edges (a value from one tool's output reappearing in another's arguments) are real but rare: removing them changes the result by 0.1 points, so they aren't part of the claim.
  • Our first shipped model (word and co-use edges only, 52%) lost to the plain past-task memory baseline (65%) once a reviewer added that baseline. We rebuilt around it; the v1 row stays on the chart.
  • Tool chains in real traces are shallow: only 2.8% have 3+ calls linked by data flow, so one-hop traversals are enough.
  • HydraDB's local-filesystem store can't publish index generations or hand a restarted node its write lease (no conditional PUT). Reads crawled until we moved it onto S3 (RustFS) with the indexer running.
