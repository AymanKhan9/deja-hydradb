Deja learns, in a HydraDB graph, which tools real tasks ended up needing — task words → tools, and tools that are used together or pass data to each other. Every task it serves makes the next loadout sharper.

How it works

(:Term {df}) -[:LED]-> (:Link {n}) -[:TO]-> (:Tool {uses})       a word in past tasks → the tool that solved them
(:Tool) -[:CO]-> (:CoLink {n}) -[:TO]-> (:Tool)                  used together, or a value flowed from one to the other
  • Query: vector-seed the catalog, then two HydraDB traversals — task terms → Link → Tool (weighted by learned counts and idf), and top seeds → CoLink → Tool (pulls in the second server a task needs). Rank, pack to the token budget.
  • Learning: after each task, the tools it actually called update the counts. Data flow is observed, not labelled: a value from one tool's output reappearing in another tool's arguments.
  • Store: counts live on reified Link nodes because HydraDB batches can set node properties but not edge properties. The served graph keeps term links seen ≥2 times, top 10 per term (31k links), which cuts a loadout query from ~5.8k to ~200 rows.
  • Verified: the 200 held-out loadouts read through HydraDB are identical to an in-memory twin of the same model; the 8,612-task learning curves are computed with that twin (a per-task HydraDB replay takes over an hour on this laptop).
  • Data: Toucan-1.5M — real MCP servers, real executed tool calls. 8,612 unique prompts, 2,236 tools across 367 servers, pooled into one catalog.

Under load

What we measured and threw away

  • Shared entity memory (“reuse IDs other agents resolved”) was our first headline. It failed its own kill test: binding precision 21%, and even a perfect binder adds only 6.3% of lookups beyond a plain (tool, args) cache.
  • Tool chains in real traces are shallow: only 2.8% have 3+ calls linked by data flow. So we use one- and two-hop traversals and don't pretend to need deep path search.
  • 40% of repeated identical tool calls return a different result — caching tool outputs blindly is unsafe.
  • HydraDB's local-filesystem store can't publish index generations or hand over a write lease (no conditional PUT) — reads crawled until we moved it onto S3 (RustFS) with the indexer running.
